Final Architecture: Adaptive Commitment Timing
Working title
Belief-Deadline Optimal Stopping for Fault-Tolerant Cluster Scheduling
or, for the hackathon:
Adaptive Commitment Timing (ACT) — an agent that decides not only where to place a task, but when it is worth committing the task to a node under uncertain node health.
The important distinction is:
Normal scheduler:
“Which node should I use right now?”
Our scheduler:
“Should I commit this task to any node now, or is it worth paying the cost of waiting for more information?”
That is the core idea.
1. Problem formulation
The environment has hidden node health.
For each node \(j\):
$$ S_j(t)\in\{H,D,X\} $$
where:
\(H\) = healthy
\(D\) = degraded
\(X\) = down
The agent never directly observes \(S_j(t)\).
Instead it receives telemetry:
$$ Y_j(t)= (\text{heartbeat},\text{latency},\text{error rate},\text{etc.}) $$
and, for tasks currently running on a node, it also obtains information through observed task progress/stalling.
Therefore the agent maintains a belief:
$$ b_j(t)= [P(S_j=H),P(S_j=D),P(S_j=X)] $$
rather than a hard:
healthy / unhealthy
classification.
This is important because a node can be uncertain.
Example:
$$ b_j=[0.55,0.35,0.10] $$
means:
“Probably healthy, but there is substantial uncertainty.”
A threshold-based scheduler would immediately classify it.
ACT does not.
2. Bayesian hidden-health inference
For every node maintain:
$$ b_j^t $$
After receiving telemetry:
$$ b_j^{t+1}(s') \propto P(Y_j^{t+1}|S_j^{t+1}=s') \sum_s P(S_j^{t+1}=s'|S_j^t=s)b_j^t(s) $$
In matrix notation:
Prediction
$$ \hat b_j^{t+1}=b_j^tP $$
Observation update
$$ b_j^{t+1}(s) = \frac{ P(Y_j^{t+1}|s)\hat b_j^{t+1}(s) }{ \sum_{s'}P(Y_j^{t+1}|s')\hat b_j^{t+1}(s') } $$
where \(P\) is the health transition matrix.
The agent therefore has a probabilistic health state, not a heuristic health score.
3. Important simulator-specific observations
These came from auditing the supplied environment/source:
Telemetry is passive
Every node emits telemetry every timestep.
Therefore:
We do NOT need to deliberately assign a task to a node just to probe it.
This is important.
The information from telemetry is available even when a node has no task.
So the primary value of waiting is:
$$ \text{better future decision} $$
rather than:
“let's send a test task and see what happens.”
That makes the optimal-stopping formulation cleaner.
4. The fundamental control variable
For a pending task \(k\), there are two conceptual actions:
$$ A_k(t)\in\{\text{HOLD},\text{COMMIT}\} $$
HOLD
Don't assign the task yet.
The task remains:
node = None
The agent receives another observation next timestep.
But holding is not free.
The simulator charges:
$$ -0.01 $$
per timestep while a task remains unassigned.
Therefore:
$$ \text{HOLD cost}=0.01 $$
per step.
COMMIT
Choose a feasible node:
$$ j^*=\arg\max_j Q_k(j,t) $$
and assign the task.
So:
$$ C_k(t)=\max_j Q_k(j,t) $$
where \(Q_k(j,t)\) is the predicted value of committing task \(k\) to node \(j\).
5. Optimal stopping formulation
Define:
$$ V_k(X_k,t) $$
as the value of the task's current decision state.
Then:
$$ V_k(X_k,t) = \max \left[ C_k(X_k,t), H_k(X_k,t) \right] $$
where:
Commitment value
$$ C_k(X_k,t) = \max_j Q_k(X_k,j,t) $$
Hold value
$$ H_k(X_k,t) = -0.01+ E[ V_k(X_k',t+1) ] $$
Therefore:
$$ \boxed{ V_k=\max(C_k,H_k) } $$
and the decision becomes:
$$ \boxed{ \text{COMMIT if }C_k\ge H_k } $$
otherwise:
$$ \boxed{ \text{HOLD} } $$
This is the central equation of the project.
6. Why this is different from threshold scheduling
A conventional system might say:
if probability(node unhealthy) > threshold:
    don't use node
or:
if latency > threshold:
    reroute
ACT doesn't have a fixed threshold.
It asks:
$$ \text{Is the value of acting now greater than the value of waiting?} $$
So even a node with moderately bad health might be selected if:
the deadline is close,
the task has already accumulated progress,
alternatives are overloaded,
recovery probability is high,
waiting costs too much.
Conversely, even a seemingly good node might not be used immediately if:
the task has lots of slack,
uncertainty is high,
waiting is cheap,
another node is expected to become safer.
That is the research idea.
7. Task state
The theoretical task state is:
$$ X_k(t)= ( b(t), r_k(t), \delta_k(t), c_k(t), \Theta(t) ) $$
where:
\(b(t)\)
All node health beliefs.
$$ b(t)=\{b_1(t),...,b_N(t)\} $$
\(r_k(t)\)
Remaining work.
\(\delta_k(t)\)
Remaining deadline.
\(c_k(t)\)
Current assignment.
For example:
None
node_3
node_7
\(\Theta(t)\)
Relevant cluster/task context:
capacity
current node occupancy
other task assignments
task queue
etc.
8. The critical correction: this is NOT an independent per-task exact Bellman problem
This is something I want Antigravity to understand.
The mathematical formulation is elegant, but the real environment has multiple tasks competing for node capacity.
Therefore the exact global state is coupled.
If ten tasks all want node 3:
$$ Q_1(3),Q_2(3),...,Q_{10}(3) $$
cannot independently be maximized.
The actual problem is closer to a coupled POMDP/scheduling problem.
So we should not pretend that we have solved the exact global Bellman equation.
Instead:
use optimal stopping as the decision principle, and implement a receding-horizon approximate solver.
This distinction makes the research claim much more defensible.
9. Commitment value \(Q_k(j,t)\)
For every task/node pair:
$$ Q_k(j,t) $$
should estimate:
expected future reward if task \(k\) commits to node \(j\) now.
The environment reward is approximately:
Completion
$$ +1 $$
Deadline miss
$$ -1 $$
Pending holding
$$ -0.01/timestep $$
There is no explicit churn penalty.
However, churn has an implicit cost because moving a task to another node causes lost progress.
10. Restart cost
This is extremely important.
Suppose:
task duration = 8
and it has already executed:
5 steps
so:
$$ r=3 $$
If it remains on the same node, its progress continues.
If it is rerouted to another node, the environment resets the task's remaining duration to the original duration.
So it effectively loses:
$$ 8-3=5 $$
steps of work.
Therefore:
$$ Q_{\text{reroute}} $$
must incorporate this restart/rework consequence.
This gives us a principled reason not to reroute every time a node looks slightly suspicious.
11. Running tasks require a slightly different interpretation
This is another correction we should preserve.
For a pending task:
HOLD
means:
remain unassigned.
For a running task:
WAIT
doesn't mean unassigned.
It means:
stay on the current node and continue executing.
Therefore the action set is:
$$ \{\text{STAY},\text{REROUTE},\text{WAIT/CONTINUE}\} $$
but STAY/WAIT is really the continuation action.
There is no -0.01 holding cost for simply keeping a running task alive.
So Antigravity must not blindly apply:
$$ H=-0.01+EV' $$
to running tasks.
For a running task:
$$ H_{\text{run}} = E[V(X_{t+1})|\text{STAY}] $$
with the actual task progress transition.
12. Pending-task decision
For a pending task:
1. Calculate value of committing now.
2. Calculate expected value of waiting one step.
3. Compare.
Commit
$$ C_k= \max_{j\in feasible} Q_k(j) $$
Hold
$$ H_k= -0.01+ E[V_k(t+1)] $$
Then:
if C >= H:
    assign
else:
    leave unassigned
13. Running-task decision
For a running task on node \(c\):
Stay
$$ Q_{\text{stay}} = E[V(X_{t+1})|\text{stay on }c] $$
Reroute
$$ Q_{\text{reroute}} = \max_{j\neq c} Q_k(j) $$
including restart loss.
Then:
$$ A_k= \arg\max \{ Q_{\text{stay}}, Q_{\text{reroute}} \} $$
But we should avoid pointless switching when the values are nearly equal.
Not through an arbitrary health threshold, but naturally through the restart cost.
14. Why churn gets controlled naturally
Suppose:
Current node
$$ Q_{\text{stay}}=0.72 $$
Alternative
$$ Q_{\text{reroute}}=0.74 $$
Naively:
reroute because 0.74 > 0.72.
But rerouting causes progress loss.
Once that restart cost is included:
$$ Q_{\text{reroute}} \rightarrow 0.55 $$
so:
$$ Q_{\text{stay}}>Q_{\text{reroute}} $$
and the task remains where it is.
Thus low churn emerges from the economics of the environment rather than:
if switched_recently:
    don't switch
or:
if health < 0.4:
    reroute
15. Finite horizon
Tasks have relatively short lifetimes.
Therefore we should not pretend we need an infinite-horizon Gittins-index formulation.
Instead use finite-horizon prediction.
For each candidate node:
$$ Q_k(j,t) $$
can be calculated over:
$$ h\leq \delta_k $$
future steps.
For example:
deadline = 8
means there is no reason to simulate 500 future timesteps.
This makes approximate dynamic programming computationally practical.
16. Predictive node model
For each node, take the current belief:
$$ b_j(t) $$
and propagate it:
$$ b_j(t+1)=b_j(t)P $$
then:
$$ b_j(t+2)=b_j(t)P^2 $$
and so on.
This lets us estimate future health probabilities.
For example:
$$ P(S_j(t+\tau)=H) $$
can be calculated directly.
Then estimate task completion under those possible health trajectories.
17. Progress model
From the actual environment:
Healthy
Progress deterministically:
$$ r_{t+1}=r_t-1 $$
Degraded
Progress is stochastic:
$$ r_{t+1}= \begin{cases} r_t-1 & p=0.5\\ r_t & p=0.5 \end{cases} $$
Therefore expected progress is:
$$ E[\Delta r]=-0.5 $$
per timestep while degraded.
Down
$$ r_{t+1}=r_t $$
So:
$$ Q_k(j,t) $$
must not simply use:
$$ P(\text{healthy}) $$
as a score.
It needs to propagate expected task progress/deadline completion.
18. Candidate-node value
Conceptually:
$$ Q_k(j,t) = E[ R_k \mid X_t, a_t=\text{assign}(k,j) ] $$
where \(R_k\) is eventual task reward.
The implementation can estimate this by forward simulation.
For each candidate:
for future step:
    propagate node-health distribution
    propagate task progress
    propagate deadline
    account for failure/recovery
    calculate probability of completion
Then:
$$ Q \approx P(\text{complete})- P(\text{miss}) - \text{restart cost} $$
with the exact simulator reward structure respected.
19. Don't oversimplify \(Q\)
Antigravity should not implement:
Q = healthy_probability - queue
That would destroy the research idea.
Instead \(Q\) should reflect:
current health belief
predicted health evolution
remaining work
deadline
current progress
restart loss
capacity
node occupancy
task competition
20. Holding value
This is where the interesting part happens.
Suppose:
Task A:
remaining work = 4
deadline = 9
There is lots of slack.
Current best node:
$$ C=0.61 $$
But waiting one step may improve the decision because telemetry arrives.
Suppose:
$$ H=0.68 $$
Then:
$$ H>C $$
so:
HOLD
The agent waits.
Next timestep the node belief might become:
$$ b=[0.1,0.2,0.7] $$
and a different node may become clearly preferable.
The agent then commits.
That is the behavior we want.
21. Why waiting is not free
Because:
$$ H=-0.01+EV' $$
If the task waits unnecessarily, it accumulates:
$$ -0.01 $$
each timestep.
Eventually:
$$ C>H $$
and the system commits.
So ACT should naturally produce:
uncertain + lots of slack
        ↓
       HOLD
        ↓
more information
        ↓
decision becomes clearer
        ↓
COMMIT
rather than waiting forever.
22. The “stopping advantage”
For implementation, define:
$$ A_k(t)=C_k(t)-H_k(t) $$
Then:
\(A>0\)
Commit.
\(A<0\)
Hold.
This quantity is useful for debugging and explanation.
Example:
Task 17
best node = 4
commit value = 0.71
hold value = 0.76
advantage = -0.05
decision = HOLD
This is a much better explanation than:
“Node health below threshold.”
23. Capacity coupling
This is one of the hardest practical pieces.
Suppose three tasks want node 2.
We can't simply do:
for task:
    choose argmax Q
because capacity can be exceeded.
Instead calculate candidate values first.
Then perform a global feasible assignment.
A useful formulation is:
$$ \max_{x_{kj}} \sum_{k,j}x_{kj}Q_{kj} $$
subject to:
$$ \sum_j x_{kj}\leq1 $$
for every task \(k\), and:
$$ \sum_k x_{kj}\leq Capacity_j $$
for every node \(j\).
For pending tasks, some tasks can remain unassigned:
$$ \sum_jx_{kj}=0 $$
if HOLD is selected.
24. Stopping + assignment integration
This means the process is:
Stage 1
Calculate:
$$ C_k=\max_jQ_{kj} $$
Stage 2
Estimate:
$$ H_k $$
Stage 3
Determine:
$$ A_k=C_k-H_k $$
Stage 4
Tasks with:
$$ A_k\leq0 $$
remain pending.
Tasks with:
$$ A_k>0 $$
become commitment candidates.
Stage 5
Solve the capacity-constrained assignment for those candidates.
This preserves the optimal-stopping idea without pretending tasks are independent.
25. Possible shadow-price improvement
If capacity contention becomes computationally difficult, introduce a node capacity shadow price:
$$ \mu_j $$
Then use:
$$ \tilde Q_{kj} = Q_{kj}-\mu_j $$
where heavily contested nodes acquire larger \(\mu_j\).
Then assignment uses:
$$ \arg\max_j (Q_{kj}-\mu_j) $$
This is a capacity dual approximation, not part of the core novelty.
Use it only if needed.
26. Receding-horizon implementation
We should not try to solve the entire infinite cluster problem.
Every timestep:
OBSERVE
   ↓
UPDATE BELIEFS
   ↓
PREDICT
   ↓
CALCULATE Q
   ↓
CALCULATE HOLD VALUE
   ↓
DECIDE COMMIT / HOLD
   ↓
CAPACITY-CONSTRAINED ASSIGNMENT
   ↓
EXECUTE
   ↓
NEXT TIMESTEP
This is essentially a receding-horizon approximate optimal-stopping controller.
27. Expected value of waiting
Theoretically:
$$ H=-0.01+E[V(X_{t+1})] $$
The difficult part is that:
$$ X_{t+1} $$
depends on the next observation.
We don't know exactly what telemetry will arrive.
Therefore Antigravity can approximate it.
Practical method
Sample plausible next observations.
For example:
sample observation 1
sample observation 2
sample observation 3
...
For each:
update belief
recalculate Q
calculate V
Then:
$$ H \approx -0.01+ \frac1M \sum_{m=1}^{M} V(X_{t+1}^{(m)}) $$
This is a Monte Carlo approximation to the continuation value.
28. But don't over-engineer it initially
First implementation should use:
$$ H\approx -0.01+ V(\text{predicted next belief}) $$
or a small number of observation samples.
We need a working baseline before implementing full stochastic lookahead.

32. What we should NOT claim
This is extremely important for the presentation.
Do not claim:
“We invented optimal stopping.”
We didn't.
Optimal stopping is established mathematics.
Instead say:
“We formulate fault-tolerant cluster scheduling as an adaptive commitment-timing problem under partially observed node health.”
And:
“The agent explicitly values the option to delay commitment rather than forcing immediate placement.”
And:
“The same decision principle is extended to rerouting by comparing continuation value against the value of restarting elsewhere.”
That is defensible.
33. The actual novelty claim
Our novelty is therefore the formulation and control mechanism, not inventing a new mathematical field.
The key idea:
Existing health-aware schedulers primarily decide which node to use based on current/predicted health. ACT introduces a second control dimension: when to commit.
The scheduler therefore controls:
$$ \boxed{ \text{where}+\text{when} } $$
instead of only:
$$ \text{where} $$
And the timing decision is derived from:
$$ \boxed{ \text{commitment value} \quad vs\quad \text{continuation value} } $$
under:
hidden node health
deadlines
restart cost
capacity constraints
stochastic recovery/failure.
34. What makes it particularly suitable for this PS
The problem explicitly gives us:
Hidden health
→ Bayesian belief.
Detection latency
→ waiting can improve information, but has a cost.
Low churn
→ rerouting has restart/progress cost.
Useful work on time
→ completion/deadline reward drives commitment.
Tasks can remain unassigned
→ HOLD is actually implementable.
Telemetry every step
→ waiting naturally produces more information.
Node recovery
→ don't permanently blacklist nodes.
That combination makes the stopping formulation very natural.
